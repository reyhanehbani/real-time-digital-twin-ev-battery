## 1. Overview

This document defines the system requirements for the **BMS-oriented, software-based real-time Digital Twin of a 355-V-class Lithium-ion EV battery pack**.

The purpose of this document is to convert the project definition from Day 0 into a clear set of requirements that can guide the design, implementation, testing, and final validation of the system.

The requirements are organized around the main engineering areas of the project:

1. Functional Requirements
2. Non-Functional Requirements
3. Battery Monitoring Requirements
4. Drive-Cycle Requirements
5. State Estimation Requirements
6. Validation Requirements
7. Fault Injection Requirements
8. Replay Requirements
9. Communication Requirements
10. HMI Requirements
11. Security Requirements
12. Command Requirements

The requirements are intentionally written so that they can later be mapped to system architecture components, software modules, test cases, and final project results.

---

# 2. System Requirement Philosophy

The system should not be treated as a collection of independent software demonstrations.

The requirements therefore focus on the behavior of the complete system and the interfaces between its major components.

The intended chain is:

```text
Drive Cycle
      ↓
Vehicle Operating Conditions
      ↓
Power Demand
      ↓
Battery Current
      ↓
Battery Virtual Plant
      ↓
Battery Measurements
      ↓
State Estimation
      ↓
BMS Monitoring
      ↓
Fault / Alarm Evaluation
      ↓
Validation
      ↓
JSON
      ↓
MQTT
      ↓
FastAPI
      ↓
React HMI
```

Each major stage should have a clear responsibility and a defined interface.

The system should also remain modular enough that an individual component can be tested without requiring the entire system to be running.

# 3. System-Level Requirements

## SYS-REQ-001 — Complete Digital Twin Pipeline

The system shall provide an integrated software pipeline connecting vehicle operating conditions, battery simulation, state estimation, BMS monitoring, validation, communication, backend processing, and web-based visualization.

---

## SYS-REQ-002 — Software-Only Implementation

The system shall operate without requiring physical battery hardware, physical sensors, embedded BMS hardware, PLC hardware, or industrial HMI hardware.

---

## SYS-REQ-003 — Battery System Representation

The system shall represent a 355-V-class Lithium-ion EV battery pack through a mathematical and simulation-based virtual plant.

---

## SYS-REQ-004 — Modular Architecture

The system shall be divided into independently maintainable functional components with defined responsibilities and interfaces.

---

## SYS-REQ-005 — End-to-End Traceability

Major requirements shall be traceable to their implementation, test cases, and validation results.

# 4. Functional Requirements

Functional requirements define what the system must actually do.

## 4.1 Battery Simulation Functions

### FR-001 — Battery Simulation

The system shall simulate the dynamic behavior of the battery pack under changing operating conditions.

### FR-002 — Battery Measurements

The simulation shall provide at least:

- Pack voltage
- Battery current
- Battery temperature
- Battery power
- Reference SoC
- Relevant internal model states

### FR-003 — Battery Power

The system shall calculate battery power from the selected voltage and current convention.

The implementation shall clearly define the sign convention for charging and discharging.

### FR-004 — Bidirectional Operation

The battery model shall support both discharge and charging operation.

### FR-005 — Regenerative Braking

The system shall support regenerative braking conditions in which vehicle energy can flow back toward the battery.

### FR-006 — Operating Conditions

The battery model shall respond to changing operating conditions generated by the vehicle and drive-cycle layer.

---

# 5. Vehicle and Drive-Cycle Functional Requirements

### FR-007 — Drive-Cycle Input

The system shall accept a time-based EV driving cycle as an input to the vehicle simulation.

### FR-008 — Vehicle Speed

The drive-cycle layer shall provide vehicle speed as a function of time.

### FR-009 — Acceleration

The system shall derive or calculate vehicle acceleration from the drive-cycle information where required.

### FR-010 — Power Demand

The vehicle model shall calculate vehicle power demand from the selected vehicle and drive-cycle parameters.

### FR-011 — Battery Power Demand

The system shall convert vehicle power demand into a corresponding battery power demand.

### FR-012 — Battery Current

The system shall calculate the battery current required to satisfy the calculated battery power demand.

### FR-013 — Braking Detection

The system shall identify operating regions associated with vehicle deceleration or braking.

### FR-014 — Regenerative Charging

When regenerative braking is enabled and operating limits allow it, the system shall represent the corresponding charging power/current behavior.

### FR-015 — Drive-Cycle Reproducibility

The same drive-cycle configuration and model parameters shall produce reproducible simulation results under the same initial conditions.

# 6. BMS Monitoring Requirements

The monitoring layer is responsible for interpreting battery information from a BMS-oriented perspective.

## 6.1 Electrical Monitoring

### BMS-001 — Voltage Monitoring

The system shall continuously monitor battery pack voltage.

### BMS-002 — Current Monitoring

The system shall continuously monitor battery current.

### BMS-003 — Power Monitoring

The system shall calculate and monitor battery power.

### BMS-004 — SoC Monitoring

The system shall monitor the estimated State of Charge produced by the state-estimation layer.

### BMS-005 — Temperature Monitoring

The system shall monitor battery temperature.

---

## 6.2 Cell-Level Monitoring

### BMS-006 — Cell-Level Information

The system shall support selected cell-level information for BMS monitoring purposes.

The system does not require a complete independent estimator for every simulated cell.

### BMS-007 — Minimum Cell Voltage

The monitoring layer shall determine the minimum cell voltage when cell-level data is available.

### BMS-008 — Maximum Cell Voltage

The monitoring layer shall determine the maximum cell voltage.

### BMS-009 — Cell Voltage Spread

The system shall calculate the voltage difference between the highest and lowest monitored cells.

Conceptually:

```text
Cell Voltage Spread
=
Maximum Cell Voltage
-
Minimum Cell Voltage
```

### BMS-010 — Abnormal Cell Identification

The system shall identify a cell or cells whose simulated behavior violates the defined monitoring limits.

---

## 6.3 Condition Monitoring

### BMS-011 — Battery Condition

The system shall evaluate the overall battery operating condition.

The initial condition levels shall be:

```text
NORMAL
WARNING
CRITICAL
```

### BMS-012 — Threshold Evaluation

The monitoring layer shall compare monitored variables against defined thresholds.

### BMS-013 — Condition Independence

Condition-monitoring logic shall remain separate from the React visualization layer.

### BMS-014 — Communication Status

The monitoring system shall include communication status as part of the overall system condition.

### BMS-015 — Alarm Generation

The monitoring layer shall generate structured alarm information when a defined abnormal condition occurs.

---

# 7. Drive-Cycle Requirements

The drive-cycle subsystem is responsible for creating realistic operating conditions for the virtual battery.

## DC-001 — Realistic Driving Input

The primary battery operating input shall originate from a realistic or defined EV drive cycle rather than a random current generator.

## DC-002 — Time-Based Drive Cycle

The drive cycle shall contain at least:

- Time
- Vehicle speed

Additional signals may be included when available.

## DC-003 — Variable Operating Conditions

The drive cycle shall contain changing operating conditions rather than only a constant-speed profile.

## DC-004 — Acceleration Conditions

The selected scenarios shall include acceleration regions.

## DC-005 — Cruising Conditions

The selected scenarios should include cruising or relatively stable-speed regions where applicable.

## DC-006 — Deceleration Conditions

The drive cycle shall include deceleration behavior.

## DC-007 — Braking Conditions

At least one validation scenario should contain braking or regenerative-braking conditions.

## DC-008 — Standstill

The system shall support periods in which vehicle speed is zero or close to zero.

## DC-009 — Power Conversion

The system shall convert the vehicle operating profile into vehicle power demand.

## DC-010 — Battery Demand

The vehicle power model shall provide the battery layer with a corresponding power requirement.

## DC-011 — Sign Convention

The system shall use a documented sign convention for:

- Vehicle power
- Battery power
- Battery current
- Regenerative charging

## DC-012 — Drive-Cycle Selection

The system shall support selecting between available drive-cycle datasets or scenarios.

## DC-013 — Drive-Cycle Metadata

Each drive-cycle scenario should have identifiable metadata such as:

- Scenario name
- Duration
- Sampling interval
- Source or generation method
- Relevant vehicle parameters

## DC-014 — Drive-Cycle Validation

The drive-cycle input shall be checked for invalid or incomplete data before being used by the simulation.

# 8. State Estimation Requirements

The state-estimation layer is one of the core BMS-oriented components of the project.

## 8.1 EKF Requirements

### EST-001 — EKF Implementation

The system shall implement an Extended Kalman Filter for battery state estimation.

### EST-002 — Primary Estimated State

The primary estimated state shall be:

```text
State of Charge (SoC)
```

### EST-003 — Additional States

The estimator may estimate additional internal battery states depending on the selected battery model.

### EST-004 — Pack-Level Estimation

The primary EKF shall initially operate on the equivalent pack-level battery model.

### EST-005 — Measurement Input

The EKF shall use available battery measurements as inputs to the estimation process.

These may include:

- Voltage
- Current
- Temperature

depending on the final mathematical model.

### EST-006 — Prediction Step

The EKF shall perform a prediction step using the battery state model.

### EST-007 — Measurement Update

The EKF shall perform a measurement-update step using available measurements.

### EST-008 — Covariance

The estimator shall maintain covariance information associated with the estimated state.

### EST-009 — Jacobian

The EKF implementation shall calculate or provide the Jacobian information required by the selected nonlinear battery model.

### EST-010 — C++ Implementation

The main estimator implementation shall be developed in C++.

### EST-011 — Eigen

Eigen shall be used for the required matrix and vector operations.

---

## 8.2 Initial Condition Requirements

### EST-012 — Correct Initial SoC

The system shall support testing with an initial estimated SoC close to the reference SoC.

### EST-013 — Incorrect Initial SoC

The system shall support testing with a deliberately incorrect initial SoC.

For example:

```text
Reference SoC = 80%
Initial EKF SoC = 60%
```

### EST-014 — Convergence

The estimator shall be evaluated for its ability to reduce initial estimation error over time.

---

## 8.3 Measurement Quality Requirements

### EST-015 — Measurement Noise

The system shall support controlled measurement-noise scenarios.

### EST-016 — Voltage Noise

The system shall support adding controlled noise to voltage measurements.

### EST-017 — Current Noise

The system shall support adding controlled noise to current measurements.

### EST-018 — Sensor Bias

The system shall support controlled measurement bias scenarios for validation and fault testing.

---

## 8.4 Estimation Output Requirements

The estimator shall provide, at minimum:

```text
Estimated SoC
Covariance Information
Timestamp
```

Additional internal states shall be included where applicable.

The estimator output should be structured so that it can be consumed by the monitoring, validation, and communication layers.

---

# 9. Estimation Uncertainty Requirements

## UNC-001 — Uncertainty Information

The system shall expose information related to EKF estimation uncertainty.

## UNC-002 — Covariance Output

Relevant covariance information shall be available outside the estimator.

## UNC-003 — Confidence Representation

The system shall support converting estimator uncertainty into a meaningful confidence indication for the monitoring/HMI layer.

For example:

```text
HIGH
MEDIUM
LOW
```

The exact thresholds shall be defined during the estimator and monitoring design phases.

## UNC-004 — No False Precision

The HMI shall distinguish between an estimated value and a directly measured value.

---

# 10. Validation Requirements

Validation is intended to independently evaluate whether the system behaves correctly and whether the estimator performs acceptably.

## VAL-001 — Independent Validation

The system shall provide an independent Python-based validation workflow.

## VAL-002 — Reference Data

The validation system shall have access to appropriate reference or ground-truth data from the simulation environment.

## VAL-003 — Estimated Data

The validation system shall process EKF estimated states.

## VAL-004 — Actual vs Estimated SoC

The validation pipeline shall compare reference SoC against estimated SoC.

## VAL-005 — Estimation Error

The validation pipeline shall calculate estimation error over time.

---

## 10.1 Required Metrics

### VAL-006 — MAE

The system shall calculate Mean Absolute Error.

### VAL-007 — RMSE

The system shall calculate Root Mean Square Error.

### VAL-008 — Maximum Error

The system shall calculate the maximum absolute estimation error.

### VAL-009 — Convergence Time

The system shall calculate or identify convergence time for scenarios where convergence analysis is applicable.

### VAL-010 — Error Visualization

The validation system shall generate engineering plots showing:

- Reference SoC
- Estimated SoC
- Estimation error
- Relevant uncertainty information

---

## 10.2 Validation Scenarios

At minimum, the estimator shall be evaluated under:

```text
Scenario A
Correct Initial SoC

Scenario B
Incorrect Initial SoC

Scenario C
Noisy Measurements
```

Additional scenarios may be added for:

- Sensor bias
- Regenerative braking
- Different drive cycles
- Different operating conditions

---

## 10.3 Python Validation Stack

The validation workflow shall use Python-based tools according to their responsibilities.

### NumPy

For numerical operations and array processing.

### Pandas

For time-series and dataset processing.

### SciPy

For scientific computing, numerical analysis, signal processing, interpolation, optimization, and supporting validation tasks where required.

### Matplotlib

For engineering plots and validation visualization.

# 11. Fault Injection Requirements

Fault injection is required because the project is software-only and therefore needs controlled software scenarios to reproduce abnormal conditions.

## FI-001 — Fault Injection Framework

The system shall provide a controlled method for introducing predefined abnormal conditions into the simulation or data pipeline.

## FI-002 — Repeatability

Injected faults shall be reproducible using defined parameters.

## FI-003 — Fault Identification

Each fault scenario shall have an identifiable fault type and configuration.

---

## 11.1 Sensor Faults

### FI-004 — Voltage Noise Fault

The system shall support excessive voltage measurement noise.

### FI-005 — Voltage Bias Fault

The system shall support a controlled voltage measurement bias.

### FI-006 — Current Noise Fault

The system shall support excessive current measurement noise.

### FI-007 — Current Bias Fault

The system should support current measurement bias where required.

---

## 11.2 Battery Condition Faults

### FI-008 — High Temperature

The system shall support an abnormal temperature scenario.

### FI-009 — Cell Imbalance

The system shall support introducing abnormal voltage behavior in one or more simulated cells.

### FI-010 — Abnormal Cell

The system shall support identifying a deliberately abnormal cell.

---

## 11.3 Communication Faults

### FI-011 — MQTT Disconnection

The system shall support simulating loss of MQTT communication.

### FI-012 — Communication Recovery

The system shall support testing system behavior after communication is restored.

### FI-013 — Communication Alarm

A communication failure shall be represented as a system condition and shall be available to the HMI.

---

## 11.4 Fault Response

For an injected fault, the system should demonstrate the following chain where applicable:

```text
Fault Injection
      ↓
Abnormal Measurement / Condition
      ↓
Monitoring Logic
      ↓
Fault Detection
      ↓
Alarm Generation
      ↓
JSON
      ↓
MQTT
      ↓
Backend
      ↓
HMI
```

# 13. Replay Requirements

Replay Mode is intended to make recorded scenarios repeatable and useful for testing and demonstration.

## REP-001 — Scenario Recording

The system shall support recording simulation and monitoring data.

## REP-002 — Recorded Dataset

A recorded scenario shall contain sufficient information to reproduce the relevant monitoring and visualization behavior.

## REP-003 — Scenario Identification

Each recorded scenario shall have an identifiable name or ID.

## REP-004 — Replay Mode

The system shall provide a Replay Mode separate from Live Mode.

## REP-005 — Replay Through Normal Pipeline

Replay data should use the same communication and visualization path as live telemetry where practical.

The intended path is:

```text
Recorded Dataset
      ↓
Replay Engine
      ↓
MQTT
      ↓
Backend
      ↓
React HMI
```

## REP-006 — Replay Timing

The replay engine shall support time-based playback.

## REP-007 — Replay Control

The system should support basic replay controls such as:

- Start
- Stop
- Reset
- Scenario selection

Additional controls may include:

- Pause
- Resume
- Playback speed

## REP-008 — Repeatability

Replaying the same dataset with the same replay configuration shall produce consistent results.

## REP-009 — Fault Replay

Recorded fault scenarios shall be replayable.

## REP-010 — Testing Use

Replay Mode shall be usable for:

- HMI testing
- Alarm testing
- Communication testing
- Demonstration
- Debugging
- Repeatable scenario analysis

# 18. HMI Design Requirements

The HMI shall follow High-Performance HMI principles and use ANSI/ISA-101-oriented thinking as a design reference.

The interface should prioritize:

```text
Situational Awareness
        ↓
System State
        ↓
Abnormal Conditions
        ↓
Trends
        ↓
Detailed Information
```

The HMI should avoid unnecessary:

- Decorative gradients
- Excessive colors
- Excessive cards
- Animation
- Visual effects
- Decorative elements

The interface shall use visual elements primarily when they communicate engineering information.

# 20. Security Requirements

Security shall be treated as an engineering requirement rather than only documentation.

## SEC-001 — Authentication

The system shall authenticate users before allowing access to protected application functions.

## SEC-002 — Authorization

The system shall distinguish between permitted and non-permitted operations.

## SEC-003 — Command Authorization

Simulation commands shall require appropriate authorization.

## SEC-004 — Secure Communication

The communication architecture shall support TLS for protected MQTT communication where applicable.

## SEC-005 — MQTT ACL

MQTT access shall use Access Control Lists where supported by the selected broker.

## SEC-006 — WebSocket Security

Where WebSockets are used for browser communication, secure WebSocket communication (WSS) shall be considered and used where applicable.

## SEC-007 — Payload Validation

Incoming commands and structured data shall be validated before being processed.

## SEC-008 — Input Validation

The backend shall validate user-provided values and command parameters.

## SEC-009 — Unauthorized Commands

Unauthorized commands shall not be forwarded to the simulator.

## SEC-010 — Invalid Commands

Malformed or invalid commands shall be rejected safely.

## SEC-011 — Credential Protection

Authentication credentials, tokens, passwords, and certificates shall not be hard-coded into publicly exposed source code.

## SEC-012 — Security Failure Visibility

Relevant security or authorization failures should be logged and made available for system diagnostics.

Python validation and data-processing workflows shall be capable of handling the generated time-series datasets without unnecessary processing overhead.

### NFR-004 — HMI Responsiveness

The HMI should update without noticeable delay during normal demonstration conditions.

---

## 22.2 Reliability

### NFR-005 — Stable Operation

The system should remain stable during normal simulation, communication, and visualization operation.

### NFR-006 — Error Handling

Subsystems shall handle expected errors without causing uncontrolled system failure.

### NFR-007 — Communication Recovery

Temporary communication failures should not permanently stop the application.

---

## 22.3 Maintainability

### NFR-008 — Modular Code

Software components shall be separated according to their responsibilities.

### NFR-009 — Clear Interfaces

Interfaces between MATLAB/Simulink, C++, Python, MQTT, FastAPI, and React shall be documented.

### NFR-010 — Configuration Separation

Important parameters such as thresholds, drive-cycle settings, and communication configuration should be separated from core application logic where practical.

### NFR-011 — Documentation

Major components shall have sufficient technical documentation for another developer or engineer to understand their purpose and usage.

---

## 22.4 Scalability

The architecture should allow the battery model to become more detailed without requiring a complete redesign of the entire system.

### NFR-013 — Extensible Monitoring

Additional monitoring and diagnostic functions should be addable without modifying unrelated components.

### NFR-014 — Extensible Drive Cycles

Additional drive-cycle scenarios should be addable without changing the core battery model.

### NFR-015 — Future Hardware Integration

The architecture should allow future integration with real BMS or battery data without requiring fundamental architectural changes.

---

## 22.5 Portability

### NFR-016 — Software-Based Execution

The core project should remain executable on a standard development computer with the required software environment.

### NFR-017 — Technology Independence by Interface

Components should communicate through defined interfaces rather than relying on tightly coupled internal implementation details.

---

## 22.6 Reproducibility

### NFR-019 — Reproducible Validation

Validation results shall be reproducible from the same input datasets and analysis configuration.

### NFR-021 — Repository

# 4. Layer Responsibilities

## 4.1 Vehicle & Drive-Cycle Layer

This layer defines the operating conditions under which the battery is evaluated.

Instead of feeding the battery model with randomly generated current, the system starts with a driving cycle. Vehicle speed is then converted into power demand, which determines the battery current required by the simulated vehicle.

```text
Driving Cycle
      ↓
Vehicle Speed
      ↓
Power Demand
      ↓
Battery Current
```

The model should be able to represent common EV operating conditions such as:

- Acceleration
- Cruising
- Braking
- Idle
- Variable load
- Regenerative braking

This gives the battery model a realistic and repeatable operating scenario.

---

## 4.2 MATLAB / Simulink Layer

MATLAB and Simulink provide the main environment for battery modeling and system simulation. They have different roles within this layer.

### MATLAB

MATLAB is mainly used for:

- Mathematical modeling
- Parameter calculations
- Battery model analysis
- Model validation
- Offline analysis

### Simulink

Simulink is used for the actual system and plant simulation, including:

- Plant implementation
- Vehicle and power simulation
- Battery pack simulation
- Measurement generation
- Fault injection
- Real-time simulation flow

The main simulation path is:

```text
Drive Cycle
     ↓
Vehicle Model
     ↓
Power Demand
     ↓
Battery Model
     ↓
V / I / T Measurements
     ↓
Fault Injection
```

The output of this layer provides the measurements and operating conditions required by the estimation and Digital Twin layers.

# 5. Battery Model Architecture

The battery is represented using a hierarchical structure:

```text
Cell
  ↓
Module
  ↓
Pack
  ↓
Vehicle
```

This structure allows the Digital Twin to maintain information at different levels of the battery system.

For the first real-time EKF implementation, however, the estimator operates on an **Equivalent Pack Model**.

```text
                 Battery Pack
                     │
        ┌────────────┴────────────┐
        │                         │
 Equivalent Pack Model       Cell-Level Representation
        │                         │
        ▼                         ▼
      C++ EKF             Monitoring / Fault Scenarios
```

This approach keeps the real-time estimator manageable while still allowing the Digital Twin to retain cell-level information for monitoring and fault-related scenarios.

The cell-level representation is therefore not discarded; it simply does not have to be part of the initial real-time EKF state vector.

---

# 6. State Estimation Layer

The C++ estimation layer receives the battery measurements generated by Simulink.

The estimator is implemented using **C++ and Eigen**, with the **Extended Kalman Filter (EKF)** as the main estimation method.

```text
V / I / T
   │
   ▼
┌──────────────────────┐
│       C++ EKF        │
│                      │
│ State Prediction     │
│ Covariance Prediction│
│ Measurement Update   │
│ Gain Calculation     │
│ State Correction     │
└──────────┬───────────┘
           │
           ▼
     Estimated State
```

The main state to be estimated is:

```text
SOC
```

Other states depend on the selected equivalent-circuit battery model.

The EKF also provides covariance information. This gives the system an indication of estimation uncertainty rather than reporting SOC as a single value with no information about confidence.

---

# 7. Digital Twin Layer

The Digital Twin acts as the software representation of the battery system.

It brings together measurements from the simulation, estimates from the EKF, and the current operating and fault status of the battery.

The Digital Twin can contain:

- Simulation measurements
- EKF estimates
- Battery state
- Temperature
- Voltage
- Current
- Cell / module / pack information
- Estimation uncertainty
- Fault status
- Alarm status

The relationship between the main components is:

```text
Simulation
     │
     ├── Measurements
     │
     ▼
    EKF
     │
     ├── Estimated SOC
     ├── Model States
     └── Covariance
             │
             ▼
        Digital Twin
             │
             ├── Current State
             ├── Historical State
             ├── Fault State
             └── Alarm State
```

The Digital Twin therefore becomes the central point for representing the current and historical state of the simulated battery.

# 24. Final Architecture Statement

The project uses a layered and modular Digital Twin architecture for a 355-V-class Li-ion EV battery pack.

MATLAB/Simulink provides the vehicle and battery simulation environment, while C++/Eigen handles real-time EKF state estimation. Python is used for offline validation, data analysis, and visualization. MQTT/Mosquitto provides the IIoT communication layer, FastAPI handles the application, backend, and security logic, and React provides the Web-based monitoring and control interface. SQLite is used for initial persistent storage, while Docker Compose provides the integration environment for the software services.

Together, these components form a single end-to-end engineering system while keeping simulation, estimation, communication, application logic, visualization, and storage clearly separated.

The architecture is designed so that each major component has a defined responsibility and interface. This makes the system easier to develop and test and also leaves room for future improvements without requiring the entire architecture to be redesigned.

The final objective is not simply to connect a collection of technologies. The objective is to build a working Digital Twin system in which battery behavior can be simulated, internal states can be estimated, faults can be introduced, data can be communicated and stored, and the resulting system state can be monitored and evaluated through a unified interface.
